## 1. 项目背景

### 1.1 市场现状

全球健康管理类应用市场持续增长。根据 Grand View Research 数据，2025 年全球健身应用市场规模约为 185 亿美元，预计 2030 年将突破 400 亿美元。然而，现有应用存在以下痛点：

| 痛点 | 描述 | 代表产品 |
|------|------|----------|
| **饮食记录繁琐** | 手动搜索、选择食物条目耗时 | MyFitnessPal |
| **AI 功能受限** | AI 功能需订阅付费，且模型能力固定 | Noom, Loba |
| **数据封闭** | 用户数据被锁在平台内，难以导出或跨平台 | 绝大多数产品 |
| **分析不够个性** | 通用建议无法满足个体差异需求 | Keep, 薄荷健康 |
| **隐私顾虑** | 饮食/健康数据上传第三方服务器 | — |

### 1.2 机遇

大语言模型（LLM）和视觉模型的快速发展带来了新可能：
- **视觉识别能力**：GPT-4o、Claude 4、Gemini 2.5 等具备强大视觉理解能力，可直接分析食物照片
- **API 化趋势**：各大模型厂商均提供开发者 API，按量计费，成本低廉
- **用户意识觉醒**：越来越多用户拥有自己的 API Key，期望自主掌控 AI 能力

**Fitness 的核心差异化**：让用户自行接入大模型 API Key，以极低成本获得专业级 AI 饮食分析能力。

### 3.2 功能详细描述

#### F-01 拍照识食（核心卖点）

```
前置条件：用户已配置 Vision API Key
输入：食物照片（拍照 / 相册选择）
处理：
  1. 图片压缩与预处理（≤ 2MB，最长边 ≤ 2048px）
  2. 调用视觉 LLM API（发送图片 + Prompt）
  3. 解析 AI 返回的食物列表与营养估算
  4. 用户确认/修正后存入饮食日志
输出：食物名称、份量、估算热量、宏量营养素
异常处理：
  - 非食物图片 → 提示用户重新拍摄
  - API 调用失败 → 降级为手动输入
  - 多食物混杂 → AI 逐项识别，用户逐项确认
```

#### F-02 语音口述记录

```
前置条件：用户已配置 LLM API Key；已授权录音权限
输入：语音录音（最长 60s）
处理：
  1. 本地 ASR 转文字（Android SpeechRecognizer）
  2. 调用 LLM API 解析自然语言描述
  3. 提取食物、份量、热量信息
  4. 用户确认后存入饮食日志
输出：同 F-01
示例输入：
  "中午吃了一份宫保鸡丁盖饭，喝了杯奶茶，还吃了两个橘子"
  → AI 解析为：
    - 宫保鸡丁盖饭 1份 ~650kcal
    - 珍珠奶茶 1杯(中) ~350kcal
    - 橘子 2个 ~80kcal
```

#### F-08 运动记录（手动/Health Connect 同步）

```
前置条件：用户已授权 Health Connect 读取权限（如需同步）
输入：手动录入 或 Health Connect 自动同步
数据来源策略：
  ┌─────────────────────────────────────────────────────┐
  │        智能手环数据同步路径                            │
  │                                                      │
  │  ┌──────────┐     ┌─────────────────┐                │
  │  │ 智能手环  │ ──→ │ 官方 App          │                │
  │  │ (小米/   │ 蓝牙 │ (小米运动健康/    │                │
  │  │ 华为/    │     │  Huawei Health/  │                │
  │  │ 三星等)  │     │  Samsung Health) │                │
  │  └──────────┘     └────────┬────────┘                │
  │                            │ 写入                     │
  │                            ▼                          │
  │                   ┌─────────────────┐                │
  │                   │  Health Connect │ ← Android 系统  │
  │                   │  (健康数据平台)  │    级数据枢纽    │
  │                   └────────┬────────┘                │
  │                            │ 读取                     │
  │                            ▼                          │
  │                   ┌─────────────────┐                │
  │                   │  Fitness App    │                │
  │                   └─────────────────┘                │
  └─────────────────────────────────────────────────────┘

支持的数据类型（通过 Health Connect）：
  - 步数 (Steps)
  - 卡路里消耗 (Calories Burned)
  - 心率 (Heart Rate)
  - 运动记录 (Exercise Session)：跑步/骑行/游泳等
  - 睡眠数据 (Sleep)：时长、阶段
  - 距离 (Distance)
  - 基础代谢 (BMR)

手动记录：
  - 运动类型（跑步/力量/游泳/骑行/瑜伽/自定义）
  - 时长（分钟）
  - 强度（轻度/中度/剧烈）
  - AI 估算消耗热量（无手环数据时的参考值）

优势说明：
  - ✅ 无需破解各厂商私有蓝牙协议
  - ✅ 用户继续使用官方 App，无需改变习惯
  - ✅ Health Connect 是 Android 官方标准，兼容性最好
  - ✅ 一次对接，覆盖小米/华为/OPPO/三星/Garmin/Google Fit 等
  - ✅ 数据本地化，权限用户可控
```

#### F-11 多模型 API Key 管理

```
支持厂商（V1 阶段）：
  - OpenAI（GPT-4o, GPT-4o-mini）
  - Anthropic（Claude 4 Sonnet, Claude 4 Haiku）
  - Google AI（Gemini 2.5 Flash/Pro）
  - DeepSeek（DeepSeek-V3）
  - 自定义兼容端点（OpenAI-compatible API）

管理功能：
  - API Key 加密存储（Android Keystore + EncryptedSharedPreferences）
  - 连接测试（发送最小请求验证 Key 有效性）
  - 余额/用量查询（调用各厂商 billing API）
  - 模型切换（为不同功能分配不同模型）
  - 用量统计（本地统计 API 调用次数与 Token 消耗）
```

## 4. 非功能需求

### 4.1 性能要求

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 应用冷启动 | ≤ 1.5s | Android Vitals |
| 拍照到分析结果展示 | ≤ 8s（含 API 调用） | 端到端计时 |
| 语音识别响应 | 实时（边说边显） | — |
| 列表滚动帧率 | ≥ 60fps | GPU 呈现模式分析 |
| 本地数据库查询 | ≤ 50ms（10000条） | Room 性能测试 |
| APK 大小 | ≤ 40MB | APK Analyzer |
| 内存占用 | ≤ 200MB（运行时峰值） | Memory Profiler |

### 4.2 安全性要求

| 要求 | 实现方式 |
|------|----------|
| API Key 安全存储 | Android Keystore 加密 → EncryptedSharedPreferences |
| 数据传输加密 | 强制 HTTPS；API Key 仅通过 Header 传输，不记录日志 |
| 本地数据安全 | Room 数据库文件仅应用私有目录可访问 |
| 剪贴板安全 | 不在剪贴板明文存放 API Key |
| 无数据上传 | 饮食/健康数据不上传至任何服务器（API 调用除外） |

### 4.3 可用性要求

| 要求 | 描述 |
|------|------|
| 离线可用 | 核心记录功能完全离线；AI 功能需联网 |
| 降级策略 | AI 不可用时，手动输入作为保底方案 |
| 错误友好 | API 错误提供中文提示 + 重试/降级选项 |
| 无障碍 | 支持 TalkBack 屏幕阅读；对比度符合 WCAG AA |

### 4.4 兼容性要求

| 维度 | 范围 |
|------|------|
| Android 版本 | 8.0 (API 26) → 15 (API 35) |
| 屏幕尺寸 | 4.7" 手机 → 8" 小平板（竖屏优先） |
| 屏幕密度 | mdpi → xxxhdpi |
| 语言 | 简体中文（V1）、英语（V2） |

## 5. 约束与假设

### 5.1 技术约束

- 仅支持 Android 平台（V1 不考虑 iOS）
- 依赖用户自备 AI API Key（不提供内置 Key，不做后端中转）
- 不使用自有服务端（数据全部本地化 + 直连 AI API）
- 不使用 Google Play Billing（V1 阶段完全免费开源）

### 5.2 业务假设

- 假设目标用户具备基本的 API Key 获取能力（或应用内提供图文引导）
- 假设视觉模型食物识别准确率 ≥ 85%（实际取决于模型能力）
- 假设用户允许应用联网（AI 功能需要）

### 5.3 不做的事情（V1 阶段明确边界）

- ❌ 不做社区/社交功能
- ❌ 不做付费订阅
- ❌ 不做 iOS 版本
- ❌ 不做智能穿戴设备蓝牙直连（通过 Health Connect 间接同步官方 App 数据，无需破解私有协议）
- ❌ 不做食品数据库自建（依赖 AI 的知识能力）
- ❌ 不做云端同步（纯本地存储）
- ❌ 不做地图/跑步轨迹记录

## 8. 架构决策记录（ADR）

> 以下决策经 `/grill-me` 深度讨论确认，日期：2026-06-25

| # | ADR | 决策 | 理由 |
|---|-----|------|------|
| ADR-05 | **V1 目标用户** | GitHub 技术人群 + 国内为主 | GitHub 首发天然筛选；国内大模型 Key 获取门槛低 |
| ADR-06 | **智能手环同步** | Health Connect（非蓝牙直连） | 小米等国内厂商支持 HC；一次对接覆盖多品牌 |
| ADR-07 | **数据备份** | V1 本地存储 + JSON 一键导出/导入 | 轻量实现；用户自行管理备份位置 |
| ADR-08 | **AI 厂商** | V1 仅国内大模型：DeepSeek / Kimi / 通义千问 / GLM + 自定义 OpenAI 兼容端点 | 覆盖国内主流；用户可自行扩展 |
| ADR-09 | **视觉 vs 文本模型** | 分开配置两个槽位：视觉模型 + 文本模型 | 国内多数模型不支持视觉；视觉可走 OpenAI 兼容中转 |
| ADR-10 | **视觉模型缺失** | 自动提示 + 引导走语音描述路径 | 语音→文本→任何文本模型都能做食物解析 |
| ADR-11 | **语音方案** | 原生 Android SpeechRecognizer + 接口抽象 | V1 快速可用；接口层保留切换到 AI API 的后路 |
| ADR-12 | **食物库** | 个人食物库从零建立；条目=菜名+克重+热量；V1 P0 | 简单才能坚持；随用户饮食自然增长 |
| ADR-13 | **产品本质** | AI 饮食记录 App + 基础健康数据看板；不碰训练计划 | 聚焦核心价值 |
| ADR-14 | **底部导航** | 3 Tab：首页 / 数据 / 我的 | AI 顾问融合进数据 Tab 的建议卡片流 |
| ADR-15 | **数据 Tab 布局** | 本周概览 → 热量趋势 → 体重趋势 → AI 建议 → 详情入口 | 一眼看到结论，想看详情再点进去 |
| ADR-16 | **AI 顾问形态** | 主动建议卡片流 + 底部自由提问 | 解决空白对话页冷启动问题 |
| ADR-17 | **AI 错误处理** | 超时提醒 / 解析失败降级显示原始文本 / 单项可编辑删除 / 非食物提示重拍 | 覆盖 4 种典型异常场景 |
| ADR-18 | **首次启动** | 3 步引导：设目标 → 配 AI → 完成（均可跳过） | 空壳首页有引导卡片兜底 |
| ADR-19 | **桌面 Widget** | 热量圆环小组件提到 V1 | 不靠通知推送，靠视觉可见性维持留存 |
| ADR-20 | **隐私 & 数据** | 纯本地存储，无服务端，不上传任何用户数据 | 开源可审计 |
| ADR-21 | **Health Connect 降级** | 手动录入是第一公民，HC 是增强数据源；不可用时静默降级 | 覆盖非小米/Huawei 设备 |
| ADR-22 | **导出格式** | `.fitness` 文件 = 标准 JSON（无密码），纯数据不含照片 | 人可读、无摩擦 |
| ADR-23 | **照片存储** | 仅保留最近 3 天照片，自动清理 | 照片是临时确认辅助，不做长期存储 |
| ADR-24 | **餐次系统** | 4 个可自定义模板；按时间自动推断；不强制选择 | 兼容 16+8、5:2 等断食模式 |
| ADR-25 | **体重记录交互** | 卡片形态：上方大字体重 + 下方缩略折线图；点击进详情页 | HC 有数据时自动填充最新值 |
| ADR-26 | **App 名称** | **食记** | 功能直白、好记、国内友好 |
| ADR-27 | **平台策略** | 纯 Android，不做 iOS/KMP | V1 聚焦单平台快速出 MVP |
| ADR-28 | **Min SDK** | 保持 API 26 (Android 8.0) | CameraX/Health Connect 等依赖需要 |
