# 🗺️ 06 — 开发路线图

> 版本：v2.0 | 日期：2026-06-25 | 状态：已校准（经 /grill-me 深度决策）

---

## 1. 产品定义（一句话）

**食记** = AI 饮食记录 App + 基础健康数据看板。

纯本地存储 · 用户自持 API Key · 不碰训练计划 · 不做 iOS。

---

## 2. V1.0 阶段总览（18 周 / 7 个 Phase）

```
V1.0 — 食记 MVP
├── Phase 0: 项目初始化       (Week 1-2)    → 空应用跑通，CI 绿灯
├── Phase 1: 基础架构         (Week 3-4)    → 3 Tab 可导航，数据库就绪
├── Phase 2: 饮食记录核心     (Week 5-8)    → 手动+拍照+语音 三通道完整
├── Phase 3: AI 集成          (Week 9-10)   → AI 分析闭环，国内大模型接入
├── Phase 4: 健康追踪         (Week 11-12)  → 体重+运动+Health Connect
├── Phase 5: 数据看板         (Week 13-14)  → 首页+数据Tab+Widget
├── Phase 6: 打磨与测试       (Week 15-16)  → 测试达标，性能优化
└── Phase 7: 发布准备         (Week 17-18)  → GitHub Release + 应用商店
```

### Phase 3：AI 集成（Week 9-10）

**目标**：拍照识食 + 语音解析 AI 闭环。国内大模型接入。AI 错误处理覆盖。

#### 3A — AI 适配层（Week 9 前半）

| # | 任务 | 产出 |
|---|------|------|
| 3.1 | `AiService` 统一接口 | `analyzeFoodImage()` / `parseFoodDescription()` / `chat()` / `chatStream()` |
| 3.2 | 视觉模型适配器 | 自定义 OpenAI 兼容端点（支持中转 API 接入 GPT-4o / Qwen-VL 等） |
| 3.3 | 文本模型适配器 | DeepSeek / Kimi / 通义千问 / GLM |
| 3.4 | `AiServiceManager` | 服务路由：按"视觉槽位"和"文本槽位"选择适配器 |
| 3.5 | AI 响应解析器 | JSON 解析 + 容错 + 格式修正 + 结构化为 `FoodAnalysisResult` |

#### 3B — API 配置页（Week 9 后半）

| # | 任务 | 产出 |
|---|------|------|
| 3.6 | API Key 管理页面 | 厂商选择 → Key 输入 → 连接测试 → 保存（加密存储） |
| 3.7 | 模型槽位配置 | 视觉模型 选择器 + 文本模型 选择器（分开配置） |
| 3.8 | 用量统计 | 本地计数 API 调用次数 + Token 估算 + 费用展示 |
| 3.9 | 视觉模型不可用处理 | 检测到无视觉能力的模型 → 提示 + 引导走语音描述路径 |

#### 3C — 端到端连通（Week 10）

| # | 任务 | 产出 |
|---|------|------|
| 3.10 | 拍照识食 AI 连通 | 拍照→压缩→发送视觉 API→解析→确认页（可逐项编辑/删除）→保存 |
| 3.11 | 语音解析 AI 连通 | 录音→ASR→发送文本 API→解析→确认页→保存 |
| 3.12 | AI 错误处理 4 场景 | ① 超时：15s 弹窗"是否继续等待" ② 解析失败：显示 AI 原始文本+降级手动 ③ 单项错误：每项 ✏️ 编辑/🗑️ 删除 ④ 非食物：提示"未识别到食物" |
| 3.13 | AI 功能引导 | 首次使用提示配置 API Key |

**检查点 ✅**：
- [ ] 拍照→AI 分析→确认→保存 全流程走通（至少一个视觉模型）
- [ ] 语音→ASR→AI 解析→确认→保存 全流程走通（至少一个文本模型）
- [ ] API Key 可配置、可测试、加密存储
- [ ] 4 种错误场景均有对应提示和处理
- [ ] 无视觉能力模型时正确提示并引导语音路径
